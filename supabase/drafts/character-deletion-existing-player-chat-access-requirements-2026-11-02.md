# Round 39 — 確認作者刪除角色後既有玩家聊天室權限（2026-11-02）

## 使用者再次確認的既定規則

本輪使用者指出，作者刪除角色後，既有玩家能否繼續聊天已經多次確認，不應再重複詢問。正式需求如下：

- 作者刪除角色後，所有已經開始與該角色對話的玩家，都可以繼續原本的聊天室；不限定只有作者本人。
- 對其他玩家而言，角色呈現方式沿用目前「已離線」／類似「私密」的狀態。
- 角色必須立即退出公開列表、搜尋、推薦、城市地圖及相遇入口。
- 不得建立任何新的單人聊天室、群組聊天室、相遇 session 或故事 session。
- 既有聊天室的延續權限與新 session 建立權限必須分開實作；角色封存不得讓既有對話失效，也不得被用來開新對話。
- 角色及必要的角色資料／媒體需依已確認的軟刪除保留政策保存，不能因作者刪除角色就 cascade 清除既有玩家的聊天歷史。

## 與其他刪除情境的界線

- 作者主動刪除角色：依角色是否曾公開、是否有任何聊天／相遇／故事使用紀錄，決定立即永久刪除或軟刪除；但只要有既有玩家聊天室，所有該等玩家均保留原聊天室續聊權。
- 作者刪除帳號：依 Round 37 已確認政策保留角色資料、角色立繪及影片，保留歷史創作者歸屬但取消作者頁連結；角色轉為封存／私密，不可建立新 session，既有授權聊天室可繼續。
- 聊天照片 30 天清理佇列維持獨立，不因本輪角色政策變更。

## 實作驗收條件

1. 兩個以上玩家曾分別開始與同一角色聊天時，作者刪除角色後，每位玩家都能進入並延續自己的既有聊天室。
2. 既有聊天室顯示離線／私密狀態，不再顯示成可公開互動的角色。
3. 作者、既有玩家及其他登入使用者都不能為封存角色建立新單聊、群聊、相遇或故事 session。
4. 直接呼叫 RPC、Edge Function 或繞過前端的請求也必須被後端拒絕；不能只隱藏 UI 入口。
5. 對從未公開且完全沒有任何聊天／相遇／故事紀錄的角色，仍可依獨立規則立即永久刪除；這個例外不得誤套到任何已有歷史對話的角色。
6. 回歸測試必須覆蓋作者刪除角色、角色轉私密、作者帳號刪除三種不同路徑。

## 本輪狀態與安全界線

- 本輪只記錄使用者再次確認的既定產品規則，沒有修改程式碼或資料庫。
- PR #200 維持 Draft / unmerged；尚未進行任何 hosted DDL/DML、Auth/Storage mutation、Worker deployment 或 Cron。
- 後續程式查核不得再把「其他已開始聊天的玩家能否繼續聊天」列為待確認問題；應直接依上述規則設計與驗收。
